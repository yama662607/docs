# 03. 構成設計・ストーリーボード先行・根拠管理

美しい見た目を作っても、論理に飛躍があったり、発表者が中身を説明できなかったり、根拠が曖昧だったりすると、デザイン作業に入った後の手戻りが極端に高コストになります。  
スライド作成の前に「構成計画」「ストーリーボード（ゴーストデック）」「根拠・数値の検証」を通すための実務プロセスです。

---

## 1. コンパクト・デックプラン（Compact Deck Plan）

スライドを作り始める前に、1スライド1行で以下の表を作成します。各セルは可能な限り1文に収めます。

| 項目 | 記入する内容 |
|---|---|
| **Claim（主張）** | 聴衆に持ち帰ってほしい1つの結論 |
| **Audience question（聴衆の疑問）** | このスライドが「今」答える問い |
| **Proof object（証明オブジェクト）** | 図、グラフ、数式、表、写真、動画などの一次根拠 |
| **Evidence source（根拠の出所）** | 元ファイル、論文、実験データ、コード、実測値 |
| **Incoming bridge（前のつながり）** | なぜ直前のスライドからこの主張が必要になるか |
| **Outgoing bridge（次のつながり）** | この結果から次にどんな疑問・行動が生まれるか |
| **Presenter status（理解確認）** | 発表者が自分の言葉で説明できる状態か（未確認なら要確認） |

### タイトル＆ブリッジの通し読みチェック
- 表を作ったら、**「Claim」と「Bridge」の列だけを上から順番に読み上げます**。
- 新しい概念が脈絡なく登場している場合、口頭トークで誤魔化そうとせず、この段階で順番を入れ替えるか橋渡しスライドを追加します。

---

## 2. ゴーストデック / HTMLストーリーボード先行ワークフロー

本番の PowerPoint 造形や装飾に入る前に、完成度20%程度の骨子（**ゴーストデック**または**静的HTMLモック**）で構造だけを先にレビューします。

### 何を検証するか
1. **タイトル連続性（Horizontal Flow）**：タイトルだけ読んで話が完結するか。
2. **情報密度と分割判断**：文字が多すぎるスライドを分割するか、不要な詳細を Appendix へ逃がすか。
3. **根拠の有無**：図やデータが未確定の箇所を隠さず「未定／要データ」として可視化する（テンプレートを埋めるために架空の数値を捏造したり、文字を小さくして無理やり詰め込んだりしない）。
4. **抜け・重複（ギャップ）**：新しく集めるべきデータや、削れる重複スライドがどこにあるか。

### HTML ストーリーボードを活用するコツ
- AI エージェントにスライドを作らせるとき、最初からバイナリの `.pptx` を組ませるより、先に **1つのデータソース（JSON/Markdown）から「タイトル順テキスト一覧」と「16:9固定比率のHTMLプレビュー（サムネイル一覧＋拡大表示）」** を出させると、論理の飛躍・タイトルの文字切れ・密度過多を一瞬で発見・修正できます。
- 修正はその元データに戻し、確定してから本番スライドを組み立てます。

## 3. 図の契約（Figure Contract）と数値の根拠管理

### Figure Contract：図を1枚載せる前の4つの質問
証拠としてグラフや図を載せるときは、次の4点に即答できる状態にします。
1. **軸・単位・条件・比較群** は何か？
2. **聴衆に図のどこを見てほしいか**（着目すべき視覚的特徴は何か）？
3. その特徴は **どの主張を直接支えているか**？
4. この図からは **どこまでが言えて、何が過剰主張（Overclaiming）になるか**？

> **注意**：開発中の内部診断プロットやデバッグ用グラフをそのままスライドに載せないでください。「その図が聴衆のどんな問いに答えるか」を言い換えられないなら、本編から外します。

### 数値の来歴分類（Number Provenance）
主張を支える数値には、必ず単位と出所を添え、性質を区別します。
- `measured`（実験・観測による実測値）
- `literature`（引用文献からの値）
- `derived`（数式・理論から導出された値）
- `fitted`（データへのフィッティングによる推定値）
- `calibrated`（目標挙動を再現するよう調整された値）
- `assumed`（モデリングや計画上の仮定値）
- `illustrative`（傾向を示すための例示値）

**鉄則**：フィッティング値・キャリブレーション値・仮定値を、あたかも第一原理の実測結果であるかのように提示してはいけません。解釈に影響する場合はスライド上の条件行または発表者ノートで明記します。

### 科学・数理モデルを扱う発表の再現契約
シミュレーションや数理モデルで主張を立てる場合、聴衆が妥当性を検証できるレベルまで要素を明示します（特に進捗報告では必須、学会では主張に直結する部分を示し残りを Appendix へ逃がす）：
- 運動方程式または更新則・相互作用ルール
- 状態変数と状態遷移（逆遷移・減衰・確率的切り替えや条件分岐を含む）
- 初期条件・境界条件・観測量の定義と計算方法
- パラメータの単位と由来、既知の省略・近似

## 4. 発表者理解ゲートとスピーカーノート

### AIが作った内容をそのまま発表させない
AIが生成した技術解説や分析は、文章が流暢でも発表者本人が細部を説明できなければ本番の質疑で破綻します。非自明な数値・図・モデルについては事前に以下を整理します。
- 平易な言葉での意味
- 直接観測された事実と、そこからの推論の境界
- 根拠が支持する範囲と、支持しない範囲
- 想定質問と防御可能な回答

発表者が説明しづらい箇所が見つかったら、**①元データからかみ砕く、②主張を単純化・言い換える、③削除または Appendix へ移す** のいずれかを選びます。

### スピーカーノートの書き方
読み上げる長文原稿（スクリプト）ではなく、視線を落として一瞬で拾える **4行構造のメモ** にします。
- **Message**：このスライドで言い切ること
- **Point at**：図や表のどこを指し示すか
- **Transition**：次のスライドへの橋渡し文
- **Likely Q**：想定される突っ込みと答え

> **禁止**：スライド本体に「クリックで表示」「後で要差し替え」「TODO」などの制作メモや演出指示を書かないでください。それらはノートまたは作成ログに置きます。

## 5. 既存のテンプレート／既存スライドを扱うときの鉄則

「このテンプレートに合わせて」「手で作ったこのファイルを直して」という依頼では、新規作成とは真逆のルールが適用されます。

### ケースA：テンプレート準拠（Template-Following）
- **ゼロから再構築（Rebuild）せず、必ず「複製して中身を書き換える（Clone-and-Edit）」**。ゼロから似せて作り直すと、必ずフォントフォールバック・余白ズレ・マスター継承崩れが起きます。
- テンプレート側の装飾（たとえ自分の好みに合わない色帯や背景でも）は**相手のブランド規範としてそのまま維持**します。勝手に独自デザインルールで上書きしません。
- **空枠の削除**：テンプレートに4つ枠があるのに中身が3項目しかない場合、4つ目の枠（アイコン・枠・文字一式）を**丸ごと削除**します。空枠の残存は最も多い欠陥です。
- 元のテンプレート画像と出力画像を並べて目視比較し、「新しく見えるか」ではなく「**テンプレートに新しい内容が自然に入っているか**」を確認します。

### ケースB：既存の手作りデッキの部分改善（Improving Existing Decks）
- 人間がPowerPoint等で手編集したファイルが**唯一のマスター**です。構造の作り直しは行わず、**依頼された箇所だけを外科的に修正**します。
- 修正前に必ずバックアップを取り、変更前後で「意図しない箇所のレイアウト・フォント・サイズが勝手に動いていないか」を確認します。
- プレースホルダーの消し忘れ（`XXX`, `未定`, 古い年号・テンプレ残骸）を洗い出し、内容に関わる修正案は勝手に捏造せず提案して合意を得ます。
